# Памятка ассистенту преподавателя

Краткое изложение инструкции для ассистентов преподавателя по курсу «Менеджмент разработки ПО».

## Зона ответственности на семестр

- Проверять часть заданий студентов (см. категории документов ниже)
- Присутствовать в качестве наблюдателя на демо команд во время первых 2-х scrum-спринтов (всего в семестре 2 scrum-спринта и 2 kanban-каденции) и убеждаться, что команды действительно сделали и продемонстрировали функционал, который указывают в отчёте по спринту как реализованный
- Активно «окучивать» свои команды: писать PO / SM, пинать, мотивировать, помогать, эскалировать преподавателю проблемы, которые не решаются своими силами
- Зачёт ассистенту ставится за реальную помощь командам, а не «за красивые глаза»

## Три категории проверяемых документов

1. **Документ с описанием продукта и команды** (колонка «Название / описание продукта»)
	- Проверяется тщательно: должны присутствовать и быть заполнены все разделы из методички
	- Особое внимание — первоначальному бэклогу продукта: приоритизированный список user story
	- В user story ошибаются практически все: смотреть раздел «Написание user story» внизу методички с примерами типовых ошибок
	- Не должно быть мутных / размытых / непонятных или слишком больших историй, а также антипаттернов вроде «Хочу войти в личный кабинет, чтобы войти в личный кабинет» в качестве первой истории
2. **Документы с выполненными заданиями по продукту** (колонки «Lean Canvas», «Продуктовое исследование», «Продуктовые метрики», «Макеты / USM», «Аудит команды», «HR»)
	- Проверяются поверхностно: главное — наличие всех разделов, описанных в методичке
	- Явные недочёты фиксировать; более глубокие замечания преподаватель напишет сам при перепроверке
3. **Отчёты по scrum-спринтам и kanban-каденциям**
	- Проверяются ассистентом самостоятельно, практически без участия преподавателя
	- Должны присутствовать все разделы из методички
	- Для scrum — убедиться на демо, что функционал, описанный как «реализованный», действительно сделан и работает

## Цветовая маркировка в таблице

- **Зелёный** — документ заполнен, замечаний нет → хвалим команду
- **Жёлтый** — документ заполнен, но есть замечания → доносим обратную связь команде
- **Красный** — грубые ошибки и косяки или не доделано (для ячейки «Дата демо 1») → доносим обратную связь команде

## Чеклист по каждой команде

### 1. Название команды и продукта

Должны быть написаны, сформулированы коротко и понятно. Если чего-то нет или название слишком длинное и переносится на несколько строк — пусть дозаполняют и сокращают.

### 2. Документ продукта

Должен существовать и быть заполнен по чеклисту:

- Название команды
- Название продукта
- Номер группы (номера групп, в которые входят студенты команды)
- Краткое описание продукта (2–4 абзаца):
	- концепция продукта (что это такое)
	- заказчик (если есть)
	- целевая аудитория приложения
	- проблема ЦА, которую решаем (потребности, которые закрываем продуктом)
	- тип ПО и платформа: web-сайт, бот для мессенджера, desktop-приложение, мобильное приложение и т. п.
- Ссылки на репозиторий и инструменты
- Список команды с ролями и компетенциями:
	- Имя Фамилия (номер группы)
	- Роль (Scrum Master, Product Owner, Team)
	- Колонки с компетенциями и уровнем владения (Backend, Frontend, Тестирование, Дизайн, DevOps)
	- Телеграм-контакты (как минимум для Product Owner и Scrum Master)
- Начальный бэклог продукта

У кого документа нет — пусть срочно создают. У кого есть, но не по формату или плохо оформлен — пусть исправляют.

### 3. Contacts of PO / SM

Должно быть ровно 2 контакта. У «цифровых кафедр» оформлено плохо — лишние контакты убрать в документ продукта.

### 4. Оформление строчки команды

Единообразные шрифты, отступы и т. п. Часть преподаватель исправил сам, остальное — силами команд или ассистента.

### 5. Lean Canvas (если ссылка проставлена)

- Документ по ссылке доступен всем желающим, без выдачи спец. разрешений
- Документ пустой или недозаполнен → пусть удаляют ссылку и ставят её, когда документ будет готов
- Заполнены все разделы; неприменимые разделы помечены явно, а не оставлены пустыми
- Содержимое действительно отвечает на вопросы соответствующих ячеек
- Отмечаем цветом по общей схеме (жёлтый / зелёный)

### 6. Дата планирования 1-го спринта

Должна быть выставлена. Если нет — выяснить причину, помочь, если в наших силах; при объективной блокирующей проблеме — эскалировать преподавателю. В любом случае — пинать и мотивировать проставить в ближайшее время.

### 7. Документ по 1-му спринту (часть 1, ДО демо)

Если назначенная дата планирования уже прошла — документ должен быть. Разделы:

- Название команды и продукта
- Номер спринта и календарный период
- Цель спринта
- Количество SP, которое берут в работу
- Sprint backlog: список user story, взятых в работу, + технические задачи, на которые разбиваются истории, с оценками в SP

Отмечаем цветом по общей схеме (жёлтый / зелёный).

### 8. Дата демо 1

Если первый спринт запланирован — дата демо тоже должна быть выставлена.

### 9. Присутствие на демо

Убедиться, что функционал, демонстрируемый как «сделанный», действительно сделан и работает. Только работающий функционал команда может отметить в документе спринта.

### 10. Документ по спринту после демо и ретро

Должны быть добавлены разделы:

- Результаты демо: список принятых историй, список отклонённых историй, ключевые замечания от заказчика / PO
- Результаты ретро: сами результаты скопированы в документ + есть ссылка на сайт с результатами ретро

Замечания от заказчика или PO, прозвучавшие на демо, должны быть зафиксированы в итоговом документе спринта. Результат проверки отмечаем цветом в ячейке «Дата демо 1» (красный / жёлтый / зелёный).

### 11. Бот studhelper

- Команды зарегистрированы в боте studhelper (http://studhelper.ru/) и зарегистрированы правильно
- После окончания спринта участники команд написали боту список выполненных задач

## Доски команд (Kaiten)

Проконтролировать наличие досок и адекватность их наполнения. Что делают неправильно:

- **Дорожка на каждого участника команды** — так точно не надо, пусть переделывают
- **Отдельные дорожки для эпиков и user story** — это перебор, тоже не нужно
- Иерархию `epic → user story → техническая задача` оформлять подчинёнными карточками, а не дорожками

## Как доносить обратную связь

- Просто написать комментарий в таблице — мало
- Нужно написать PO или SM в телеграм, смотря в чьей компетенции вопрос (по продуктовому документу — к PO)
- Контакты команд — в tg-контактах, указанных в таблице
- Если по документу были замечания и они исправлены — перепроверить и отметить цветом
